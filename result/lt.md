# 効率的なテスト観点の作り方（実例：メールアドレスの「文字数境界値」）

## 背景
- 現在、MAプロダクトを対象に **ドメイン観点の検証リスト**を作成中（画面操作＝E2E的）。
- 個人的に、メールアドレスの制約（規格や現実の扱い）をちゃんと理解していなかったので、  
  「どういう観点があり、どう効率よくテスト設計するか」を整理して共有する。

---

## メールアドレス項目はどんな検証があるか？
メールアドレスは観点が多く、素直にやるとケースが増えやすい。

例：
- 形式（`@`の有無、空白、ドット位置など）
- 文字種（`+` / `_` / `-` / 全角など）
- **文字数（今回の主題）**
- 重複（同じアドレスの二重登録など）

---

## メールアドレスの基準（RFCは土台）
メールアドレスには RFC という規格がある。
- RFC 5321：SMTP（メールを配送する側の仕様。アドレス長などの制約が関わる）
- RFC 5322：メールメッセージ形式（ヘッダ等）やアドレス表現の文法に関わる

> ポイント：**RFCは土台**だが、**RFC準拠＝常に正解**ではない。

### なぜRFCだけで決めきれない？
現実のメール運用では「相互運用性」「実装」「プロバイダ固有ルール」があるため。
例としてGmailはユーザー名のドットの扱いなど独自ルールがある（※ただしこれはGmail固有）。  
→ MAは任意ドメインを扱うので、特定プロバイダのルールをそのまま一般化すると事故る。

結論：
- **RFCを土台**にしつつ
- **プロダクト要件（何を通し、何を防ぐか）**で合理的な制約を決める

---

## 今日のテーマ：文字数制限はどこまでテストする？
文字数制限は分解するとこうなる：
- **local の長さ**（`@`より前）
- **domain の長さ**（`@`より後）
- **total の長さ**（`local@domain` 全体）

素直に境界値を並べると、例えば：
- local：64 / 65
- domain：255 / 256
- total：254 / 255
…と増えがち。

---

## 全部テストする？ → しない（削る理由）
### 重要ポイント：E2Eでは「到達できる境界」を優先する
E2E（画面操作）は1ケースの追加コストが高い。  
だから **到達しやすく、壊れたときの影響が大きい境界**を優先する。

- **local 64/65**：入力で現実に起きやすい＆根拠を説明しやすい（RFC由来）
- **total 254/255**：後工程（保存・配信・連携）で破綻しやすい境界

### domain 255/256 をE2Eでやらないことがある理由
多くの実装は total に上限（例：254）を置くことが多い。  
この場合 `local@domain` の構造上、
- `@` の1文字が必ず入り
- localも最低1文字は必要
→ domainだけ255まで伸ばす入力は **現実的に到達しにくい / 冗長**になりやすい。

👉 「domain境界を追加しても新しい情報が増えない」なら削るのが合理的。

※例外：
domain側の“別制約”（例：DNSラベル長など）まで保証する方針なら、代表1本だけ足す。

---

## おすすめ最小セット（例）
- local：64 OK / 65 NG
- total：254 OK / 255 NG（プロダクト方針に合わせる）
- domainは基本スキップ（冗長になりやすい）
  - 例外：別制約を保証したい場合のみ代表を追加

---

## 感想
- “正解がない”入力制約でも、  
  **ドメイン（守りたい価値）→ 技法（境界値/同値）→ 最小セット**  
  の流れに落とすと説明可能になる。
- 増やすより「削る判断」を言語化できると、検証リストの価値が上がる。
