**クリーンアーキテクチャを調べてみた**

## 背景

最近、業務でプロダクトの検証やバグ修正を行っています。

コードを読む中で、プロダクトではクリーンアーキテクチャ風の構成が採用されていることを知りました。

例えば、以下のような責務ごとにディレクトリやファイルが分かれています。

ただ、自分は最初からそれぞれの役割を明確に説明できたわけではありませんでした。

「この処理はhandlerに書くべきなのか」

「usecaseには何を書くべきなのか」

「domainとrepositoryの違いは何なのか」

「なぜこのような構成になっているのか」

といった点を理解しないまま実装すると、動くコードは書けても、設計として良い場所に書けているか判断できません。

そこで今回は、プロダクトの構成を理解するために、クリーンアーキテクチャについて調べました。

## クリーンアーキテクチャとは

クリーンアーキテクチャは、アプリケーションの中心に**業務ルール**を置き、その外側にWeb、DB、フレームワーク、UIなどの詳細を配置する考え方です。

ざっくり表すと、以下のようになります。

ここに図を引用する

単に層を分けることではありません。重要なのは、**内側にある重要なルールを、外側の詳細に依存させないこと**です。

ここでいう外側の詳細とは、例えば以下です。

- Webフレームワーク
- DB
- ORM
- HTTP
- UI
- 外部API
- ファイル入出力

これらはアプリケーションにとって重要ではありますが、業務ルールそのものではありません。

例えば、ユーザー登録という処理がある場合、

「ユーザーとして成立する条件」や「登録時に守るべき制約」は業務ルールです。

一方で、

- HTTPで受け取る
- JSONで返す
- DBに保存する
- ORMを使う

といった部分は、業務ルールを実現するための手段です。

クリーンアーキテクチャでは、この**業務ルール**と**実現手段**を分けて考えます。

クリーンアーキテクチャで特に重要だと感じたのは、以下の2つです。

```
1. 責務
2. 依存方向
```

## 責務

責務とは、簡単に言うと「そのファイル・関数・層が何を担当するのか」です。

例えば、handlerがHTTPリクエストの受け取りを担当するのであれば、

handlerに業務ルールやDB操作を大量に書くのは責務が広がりすぎている可能性があります。

逆に、repositoryがDBアクセスを担当するのであれば、

repositoryに「このユーザーはこの操作をしてよいか」といった業務判断を書くのは違和感があります。

つまり、クリーンアーキテクチャを理解することは、

**どこに何を書くべきかを判断するための基準を持つこと**につながります。

---

## 依存方向

もう1つ重要なのが依存方向です。

クリーンアーキテクチャでは、基本的に依存方向は以下のようになります。

```
外側 → 内側
```

つまり、外側は内側を知っていてよいですが、内側は外側を知りません。

例えば、

```
handler → usecase → domain
```

という依存は自然です。

一方で、domainがhandlerやWebフレームワークを知っている状態は、内側が外側に依存しているため、クリーンアーキテクチャの考え方からは外れます。

具体的には、以下のような考え方です。

- domainはDBを知らない
- domainはHTTPを知らない
- usecaseは画面表示の都合を知らない
- 業務ルールはフレームワークに依存しない
- WebやDBは、業務ルールを実行するための外側の手段である

この依存方向を守ることで、業務ルールを外側の変更から守りやすくなります。

## MAの構成

MAの設計方針では、以下のようなレイヤー構造になっています。

```
entrypoint
  ↓
application
  ↓
usecase
  ↓
domain / datasource
```

依存方向は以下です。

```
entrypoint -> application -> usecase -> domain / datasource
```

## 厳密なクリーンアーキテクチャとの違い

自社プロダクトの設計方針には、以下のような説明があります。

```
クリーンアーキテクチャライクなレイヤー構造を採用している。

ただし、usecase -> datasource はインターフェースを介さず、直接依存する。

理由は Repository インターフェースの抽象化コストに対して、
テスト時のモック差し替えの需要が低いため。
```

ここが、厳密なクリーンアーキテクチャとの違いだと理解しました。

厳密なクリーンアーキテクチャでは、usecase が datasource の具体実装に直接依存するのではなく、

usecase 側に repository interface を置くことが多いです。

```
usecase
  ↓
repository interface
  ↑
datasource implementation
```

この構成にすると、usecase は DB の具体実装を知らずに済みます。

一方、自社プロダクトでは以下です。

```
usecase -> datasource
```

つまり、usecase が datasource に直接依存しています。

そのため、厳密にはクリーンアーキテクチャではなく、

**クリーンアーキテクチャライクな構成** と表現されているのだと考えました。

## レイヤードアーキテクチャとの違い

一般的なレイヤードアーキテクチャは、以下のような構成です。

```
Controller
  ↓
Service
  ↓
Repository
  ↓
Database
```

レイヤードアーキテクチャは、層を分けることで責務を整理する考え方です。

一方で、構成によっては以下のようになりやすいです。

- Service が肥大化する
- Repository に業務ロジックが入る
- DB構造にアプリケーションが引っ張られる
- Domain がただのデータ入れ物になる
- 業務ルールがどこにあるか曖昧になる

自社プロダクトの構成は、依存方向だけを見るとレイヤードアーキテクチャに近い部分があります。

特に、

```
usecase -> datasource
```

に直接依存している点は、レイヤード的です。

ただし、単純なレイヤードアーキテクチャとも少し違います。

理由は、以下のように責務が分けられているからです。

```
entrypoint：外部からの入口
application：アプリケーション全体の調整
usecase：アプリケーション固有の処理
domain：業務ルール
datasource：DBや外部APIなどの詳細
```

特に `domain` と `datasource` が分かれていることで、

業務ルールとデータアクセスの詳細を分離しようとしている点が、クリーンアーキテクチャ寄りだと考えられます。
