# APIが遅いとき、DBでは何を見る？

## スロークエリと実行計画による一次切り分け

---

# 1. 今回のテーマ

APIや画面の応答が遅いとき、DBが原因の可能性がある場合には、次の情報を確認します。

* スロークエリ
* 実行計画

今回のゴールは、次の違いを理解することです。

> スロークエリで調査対象のSQLを特定し、
> 実行計画で遅い原因の仮説を立てる。

---

# 2. 障害調査の中での位置づけ

```text
APIや画面の遅延を検知
        ↓
ログやメトリクスから遅い箇所を確認
        ↓
DB処理が遅い可能性がある
        ↓
スロークエリから遅いSQLを特定
        ↓
実行計画から原因候補を調査
```

APIが遅いからといって、最初からDBが原因だと判断するわけではありません。

アプリケーション、DB、外部APIなどのうち、どこで時間がかかっているかを確認した上で調査します。

---

# 3. スロークエリとは

スロークエリとは、一般的には設定された時間よりも実行に時間がかかったSQLです。

障害調査では、主に次を確認します。

* 障害発生時刻に実行されていたか
* どのSQLが遅かったか
* どの程度時間がかかったか
* 何回実行されていたか
* 何行読み込み、何行返したか

例えば、次のSQLは処理量が多い可能性があります。

```text
読み込んだ行数：1,000,000行
返却した行数：10行
```

ただし、スロークエリに記録されたからといって、必ず問題のあるSQLとは限りません。

正常なバッチや集計処理も、実行時間が長ければ記録される場合があります。

---

# 4. 実行計画とは

実行計画とは、DBがSQLをどのような手順で処理するかを示したものです。

例えば、次のSQLを実行します。

```sql
SELECT id, email
FROM users
WHERE email = 'user@example.com';
```

DBには、主に次のような探し方があります。

```text
方法1：usersテーブルを先頭から確認する

方法2：emailのインデックスから対象行を探す
```

SQLには「何を取得するか」が書かれています。

実行計画には、DBが「どのように取得するか」が表示されます。

---

# 5. 実行計画で見る3つのポイント

## ① アクセス方法

テーブル全体を読んでいるか、インデックスを利用しているかを確認します。

代表例：

* Table Scan
* Sequential Scan
* Index Scan

ただし、全件走査だから必ず悪いとは限りません。

小さいテーブルや、大部分の行を取得する処理では、全件走査の方が効率的な場合もあります。

## ② 処理行数

最終的な取得件数だけでなく、途中で何行処理したかを確認します。

```text
テーブル読み込み：1,000,000行
        ↓
検索条件で絞り込み：1,000行
        ↓
最終結果：10行
```

読み込む行数が多い場合は、次の可能性があります。

* 適切なインデックスがない
* 検索条件が広すぎる
* JOIN前に絞り込めていない

## ③ 処理時間

実測情報がある場合は、どの処理に時間がかかっているかを確認します。

* テーブル読み込み
* JOIN
* ソート
* 集約

---

# 6. 実行計画の比較例

## 全件走査の場合

```text
Table Scan
  読み込み行数：1,000,000
  返却行数：1
  実行時間：800ms
```

## インデックスを利用した場合

```text
Index Scan
  読み込み行数：1
  返却行数：1
  実行時間：5ms
```

同じ結果を取得するSQLでも、DBが選択した処理方法によって、読み込むデータ量や実行時間が変わります。

その違いを確認するのが実行計画です。

---

# 7. EXPLAINとEXPLAIN ANALYZE

## EXPLAIN

```sql
EXPLAIN
SELECT id, email
FROM users
WHERE email = 'user@example.com';
```

DBが選択する予定の実行計画を表示します。

主に確認できるもの：

* アクセス方法
* 使用するインデックス
* JOINの順序
* 推定行数

## EXPLAIN ANALYZE

```sql
EXPLAIN ANALYZE
SELECT id, email
FROM users
WHERE email = 'user@example.com';
```

SQLを実際に実行し、実際の処理行数や実行時間を表示します。

ただし、実際にSQLが実行されるため、本番環境での利用には注意が必要です。

* 重いSQLを再実行すると負荷が増える
* 更新系SQLではデータに影響する可能性がある
* 障害中に実行すると状況を悪化させる可能性がある

---

# 8. まとめ

```text
スロークエリ
    ↓
どのSQLを調査するか特定する

実行計画
    ↓
SQLがどのように処理されたか確認する

ログ・メトリクス
    ↓
SQL固有の問題か、DB全体の問題か判断する
```

## 今回のポイント

1. スロークエリは、調査対象となるSQLを特定するために使う
2. 実行計画は、SQLが遅い原因の仮説を立てるために使う
3. 実行計画では、まずアクセス方法・処理行数・処理時間を見る
4. 全件走査やスロークエリだけで、問題だと断定しない
5. 実行計画だけでなく、ログやメトリクスと合わせて判断する

> スロークエリと実行計画は、
> 原因を直接示すものではなく、原因候補を絞るための情報である。
